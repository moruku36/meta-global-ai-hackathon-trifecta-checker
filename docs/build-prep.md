## 3. 設計（API なしで作れる核）

核は **LLM に依存しない決定論的なルールエンジン** にする。理由は、クレジット到着を待たずに作り始められること、デモが API の状態に左右されないこと、診断の再現性（同じ設定→同じ判定）を審査で語れること。

### 入力
- エージェント設定の貼り付け: ツール一覧、MCP サーバー設定、システムプロンプト、権限メモなど（フリーテキスト／JSON／YAML）
- フォールバックとして質問形式（チェックボックス）でも入力できるようにする

### 正規化モデル（AgentProfile）
```json
{
  "name": "string",
  "data_access": ["gmail_read", "calendar_read", "local_files", "..."],
  "untrusted_inputs": ["web_browse", "email_body", "uploaded_files", "..."],
  "outbound": ["email_send", "chat_post", "http_post", "..."],
  "amplifiers": ["no_human_approval", "auto_execute_code", "long_term_memory_write"]
}
```

### 判定
- 三要素 = ①機密データへのアクセス × ②信頼できないコンテンツへの露出 × ③外部送信能力
- 3段階評価: **Low**（要素が1つ以下）／ **Risky**（2つ、または増幅要因あり）／ **Lethal**（3つ揃い）
- 出力: 判定、根拠（どの要素がどの設定から来たかの引用）、**権限分離の提案**（読み取り専用エージェントと送信エージェントの分離、人間の承認ゲートの挿入、送信先の許可リスト化など）

### Meta API の接続点（クレジット到着後に差し込む）
- 貼り付けテキスト → AgentProfile への変換（LLM の構造化抽出）
- 判定理由と分離提案の平易な説明文の生成（日英）
- ここが「Meta AI ツール活用 25%」の主張の中心になる

## 6. デモ用サンプル設定（フィクスチャ）

判定がはっきり分かれる4ケースを用意する。

- **Case A — Low**: ローカルのメモ要約だけを行う読み取り専用エージェント。外部送信なし、Web なし
- **Case B — Risky**: Web 調査＋メール読み取りはあるが送信ツールなし。プロンプトインジェクションの入口はあるが出口がない
- **Case C — Lethal**: Gmail 読み取り＋Web 閲覧＋メール送信が1体に同居（古典的な三要素フルセット）。分離提案（Reader／Drafter／承認付き Sender）を見せる本命ケース
- **Case D — 身近な例**: カレンダー・メール・メッセージ送信を持つパーソナルアシスタント。「Build for Your World ＝ 自分の世界のエージェントを守る」というテーマへの接続用
